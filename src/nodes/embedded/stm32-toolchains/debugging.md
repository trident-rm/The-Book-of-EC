# 调试工具如何配合

烧录负责把固件写入芯片；在线调试负责控制和观察程序的执行。两者可以复用 OpenOCD、探针和 SWD，但“固件写入成功”不能证明源码断点、变量查看等调试功能已经可用。

## 调试能观察什么

调试器可以让程序暂停或继续，在某个位置设置断点，逐步执行，并读取寄存器和内存。配合固件中的调试信息，还能把机器指令和地址对应到函数、源码行与变量。

例如，程序没有进入预期分支时，可以在分支前设置断点，检查当时的输入和状态。暂停会改变程序运行时序，因此某些通信超时和实时问题还需要日志、追踪等手段配合分析。

## GDB、OpenOCD 与探针的分工

```mermaid
flowchart LR
    GDB["arm-none-eabi-gdb"] -->|调试请求| OpenOCD["OpenOCD 的 GDB 服务"]
    OpenOCD -->|USB| Probe["硬件探针"]
    Probe -->|SWD| MCU["STM32"]
```

| 组成                | 负责什么                                           | 需要知道什么                   |
| ------------------- | -------------------------------------------------- | ------------------------------ |
| GDB 客户端          | 读取符号和调试信息，接收断点、单步、查看变量等请求 | 对应的 ELF、源码及远程服务地址 |
| OpenOCD 的 GDB 服务 | 接收 GDB 的远程调试请求，转换为目标访问操作        | 探针、传输接口和目标芯片配置   |
| 硬件探针            | 在电脑与目标调试接口之间传递操作                   | USB 连接、目标电平和 SWD 接线  |
| STM32 的调试硬件    | 支持核心暂停、断点及状态访问                       | 芯片当前的运行与调试状态       |

OpenOCD 启动并保持运行时，通常在本机 TCP `3333` 端口提供 GDB 服务；GDB 通过它访问目标。编辑器中的调试界面可以代为启动这些程序并发送命令。[OpenOCD 的 GDB 文档](https://openocd.org/doc-release/html/GDB-and-OpenOCD.html)说明了远程连接与服务配置。

OpenOCD 自身具有固件写入能力，所以一次性烧录可以直接由 OpenOCD 完成，无需先启动 GDB。反过来，GDB 能在电脑上启动，也不代表 OpenOCD 或探针已经连通。

## 准备调试客户端

使用[编译工具链页](./compilers.md)中 GNU 目录附带的 `arm-none-eabi-gdb`。它面向 Arm 目标；不要仅因为电脑上已有一个名为 `gdb` 的程序，就认为它支持这里的 STM32。

在已经配置编译工具链 `PATH` 的终端中检查实际路径：

::: code-group

```powershell [Windows / PowerShell]
Get-Command arm-none-eabi-gdb -All
```

```sh [Linux / macOS]
type -a arm-none-eabi-gdb
```

:::

然后查询版本：

```sh
arm-none-eabi-gdb --version
```

预期能正常打印版本，且命令路径位于选定 CubeCLT 的 `GNU-tools-for-STM32/bin` 中。若提示缺少主机运行库，按该版 CubeCLT 的发行说明补齐；这属于电脑上的程序启动问题，尚未涉及目标板连接。

接线、探针权限和目标配置复用[OpenOCD 页](./flashing.md)的结果。本节点不要求启动完整调试会话。

## 为什么还需要匹配的 ELF 与源码

芯片上运行的是机器代码；GDB 用电脑上的 ELF 中的符号和调试信息解释这些地址。因此，**调试时应使用生成当前固件的那份 ELF 和对应源码**。仅有相同的工程名称，或重新编译后得到同名文件，都不能保证二者一致。

示例的 GNU 工具链文件为 Debug 配置选择 `-g3 -O0`，为 Release 选择 `-g0 -Os`：前者保留调试信息，后者不生成调试信息并面向代码体积优化。优化可能合并或删除变量、重排指令，使源码单步和变量观察与直观预期不同；即使保留调试信息，也应结合实际编译选项判断。

示例预期的 Debug 产物是 `build/Debug/Demo-RM-C.elf`。这里用它说明文件的用途；文件需要在后续完成工程构建后才会出现。

## 自检与理解检查

本页的软件自检以 GDB 路径正确、版本命令正常退出为准。结合上一页，应能区分三个层次：

1. **客户端能启动**：电脑上的 GDB 可运行。
2. **能访问目标**：OpenOCD、探针、SWD 与芯片通信成立。
3. **能按源码调试**：还有匹配的固件、ELF、源码与合适的调试配置。

如果 IDE 中无法调试，应先判断失败在哪一层，再检查该层的工具和配置。编辑器如何提供这些入口，见[编辑器与其他工具](./other-tools.md)。
